TYPE 뒤에 무엇을 적으면
어떤 변수가 만들어질까요?

TYPE 뒤에 지정하는 데이터 타입에 따라, 변수는 한 개의 필드, 여러 필드를 묶은 구조, 여러 행을 담는 내부 테이블이 됩니다.

기억할 점“한 칸”은 한 글자가 아니라 하나의 필드라는 뜻입니다. 예: STRING은 긴 문자열도 저장할 수 있습니다.

02 · 종류별로 살펴보기

선언 예제를 함께 확인해 보세요.
01

기본 데이터 타입 → 한 개의 필드

미리 정의된 ABAP 데이터 타입을 TYPE 뒤에 지정합니다.

TYPE 뒤의 타입분류어떤 값을 담을까?
STRING문자열길이가 변하는 문자 데이터 예: 'Hello ABAP'
C문자고정 길이의 문자 필드 예: 'SEOUL'
N숫자 텍스트숫자 모양의 문자 필드 예: '00012'
I정수소수점 없는 정수 예: 120
F부동소수점실수 계산용 근삿값
P고정 소수점자릿수를 지정하는 Packed Number 예: 1250.50
D날짜YYYYMMDD 형태 예: '20261119'
T시간HHMMSS 형태 예: '183000'
 
DATA lv_title  TYPE string.
DATA lv_code   TYPE c LENGTH 5.
DATA lv_number TYPE n LENGTH 5.
DATA lv_amount TYPE p LENGTH 8 DECIMALS 2.
ⓘ
C와 N에 LENGTH를 생략하면 기본 길이는 1입니다. P에 LENGTH와 DECIMALS를 생략하면 기본 길이 8바이트, 소수 자릿수 0입니다. STRING은 가변 길이이며, 모두 한 개의 필드입니다.
02

→ 한 개의 필드

ABAP Dictionary의 데이터 엘리먼트를 변수의 타입으로 사용합니다.

DATA lv_carrid TYPE s_carr_id.   " 항공사 ID용 데이터 엘리먼트
ⓘ
데이터 엘리먼트가 지정한 타입·길이 등 속성을 사용하여 변수를 선언합니다. 일반적으로 단일 필드가 만들어집니다. 을 정의한 데이터 엘리먼트라면 참조 변수입니다.
03

스트럭처 타입 / 투명 테이블 → 구조 변수

구조를 설명하는 타입을 지정하면, 그 안의 필드들이 하나의 변수에 묶입니다.

스트럭처 타입

Dictionary에서 정의한 스트럭처를 사용합니다.

DATA ls_item TYPE zstr_item.

※ ZSTR_ITEM은 사용자가 정의하는 예시 이름입니다.

테이블의 행 구조를 변수 타입으로 사용합니다.

DATA ls_carrier TYPE scarr.

결과: SCARR의 필드로 구성된 구조 변수 1개

ⓘ
TYPE scarr는 데이터베이스의 모든 행을 가져오는 구문이 아닙니다. SCARR의 행 구조와 같은 타입의 변수를 선언할 뿐입니다.
04

→ 인터널 테이블 변수

테이블 타입을 지정하면 같은 형태의 행을 0개 이상 담을 수 있습니다.

TYPES ty_carriers TYPE STANDARD TABLE OF scarr WITH EMPTY KEY.
DATA  lt_carriers TYPE ty_carriers.
ⓘ
ty_carriers는 프로그램 안에서 정의한 테이블 타입입니다. 같은 방식으로 Dictionary에서 미리 만든 테이블 타입도 TYPE 뒤에 지정할 수 있습니다. 여기서는 목록을 저장하는 용도로 를 사용했습니다. 키 선택 기준에서 다른 선언도 비교할 수 있습니다.

그림은 행 타입이 구조인 인터널 테이블의 예입니다. 인터널 테이블은 단일 필드를 행 타입으로 사용할 수도 있습니다. 다음의 EMPTY KEY / DEFAULT KEY / 명시적 KEY 비교에서 어떤 필드를 키로 선택할지 확인해 보세요.

03 · 인터널 테이블의 키 이해하기

EMPTY KEY · DEFAULT KEY · 직접 지정하는 KEY
05

키 필드는 어떤 기준으로 결정할까요?

키는 인터널 테이블의 행을 비교하거나 찾을 때 사용하는 필드의 조합입니다.

아래 세 선언은 모두 SCARR 한 행을 행 타입으로 사용합니다. 하지만 를 정의하는 방식이 다릅니다. 연두색 필드가 키에 포함됩니다.

키 필드를 0개로 선언합니다. 단순한 행 목록을 추가하고 순회할 때 적합합니다.

키에 포함된 필드: 없음
MANDTCARRIDCARRNAMECURRCODEURL
초록색 표시 없음
TYPES ty_empty TYPE STANDARD TABLE OF scarr
  WITH EMPTY KEY.
목록 저장 중심 / 키 필드 없음

행 타입에서 문자형·바이트형 필드를 자동으로 기본 키에 넣습니다. DB의 기본 키와는 다릅니다.

이 인터널 테이블의 DEFAULT KEY: 5개 필드
MANDTCARRIDCARRNAMECURRCODEURL
문자형이므로 모두 키에 포함
TYPES ty_default TYPE STANDARD TABLE OF scarr
  WITH DEFAULT KEY.
필드가 자동으로 선정됨 / 의도와 다를 수 있음

③ 명시적 KEY 추천 예시

조회·비교에 사용하는 필드만 직접 지정합니다. 항공사별 행을 구분하려면 CARRID가 적합합니다.

키에 포함된 필드: CARRID
MANDTCARRIDCARRNAMECURRCODEURL
항공사 코드만 키로 지정
TYPES ty_by_id TYPE STANDARD TABLE OF scarr
  WITH NON-UNIQUE KEY carrid.
CARRID를 기준으로 사용 / 중복은 허용

왜 CARRID가 좋은 키 후보일까요?

CARRID는 항공사를 식별하는 코드입니다. 반면 CARRNAME은 표시용 이름이고 CURRCODE는 여러 항공사가 공유할 수 있는 통화 코드입니다. 따라서 항공사를 식별하려는 목적에는 CARRID가 더 적합합니다.

주의: SCARR의 는 MANDT + CARRID입니다. 일반적인 단일 클라이언트 처리에서는 CARRID만 키로 쓰는 예제를 만들 수 있지만, 여러 클라이언트의 데이터를 한 테이블에 섞어 관리한다면 MANDT도 키에 포함해야 합니다.

사용 목적선언 방식이유
단순 목록 저장·순서대로 처리STANDARD ... WITH EMPTY KEY키 비교가 필요 없는 목록임을 명시
기존 코드의 기본 키 동작 유지STANDARD ... WITH DEFAULT KEY자동 선정된 문자형·바이트형 키를 사용. 선언 의도를 먼저 검토
CARRID 기준으로 행을 비교STANDARD ... WITH NON-UNIQUE KEY carrid필요한 필드만 명시. 중복 허용
CARRID별 유일한 행을 빠르게 조회SORTED ... WITH UNIQUE KEY carrid유일성 보장 및 정렬 키 기반 조회에 적합

항공사 코드로 한 행을 찾는다면? 도 알아두세요.

항공사별 한 행만 저장하고 CARRID로 반복 조회할 때는, 키를 명확하게 지정한 정렬 테이블을 사용할 수 있습니다.

TYPES ty_carriers_by_id TYPE SORTED TABLE OF scarr
  WITH UNIQUE KEY carrid.

DATA lt_carriers_by_id TYPE ty_carriers_by_id.
DATA ls_carrier        TYPE scarr.

" 항공사 코드를 기준으로 행 조회
READ TABLE lt_carriers_by_id WITH TABLE KEY carrid = 'LH'
  INTO ls_carrier.
ⓘ
혼동하지 마세요. STANDARD TABLE의 키를 직접 지정해도 중복이 자동으로 금지되거나 검색이 자동으로 빨라지는 것은 아닙니다. 유일성 보장 여부와 조회 특성은 테이블 종류(STANDARD / SORTED / HASHED)도 함께 결정합니다. 또한 WITH DEFAULT KEY의 DEFAULT는 데이터베이스 기본 키를 가져온다는 뜻이 아닙니다.

결국, TYPE을 보면 변수의 모양이 보입니다.

코드를 읽을 때 먼저 TYPE 뒤에 무엇이 오는지 확인해 보세요.
